あとの作業に影響する技術と設計の判断を、新しいものを上にして書く。理由と、採らなかった案も残す。結論を改めるときは、元の項目を消さずに、改めた日付と理由を足す。

## 2026-11-05 教科書の1首のページを、表と規則と助言の候補から組み立てる

- 決めたこと：
  - 1首のページ（`/karuta/<番号>/`、序歌は `/karuta/joka/`）は手で書かず、`site/build.ts` が組み立てのときに作る。歌と決まり字は札の読みの表（`cards.json`）から、「気をつける点」は規則（`content/karuta/rules.ts`）から、「言葉の助言」はスキルの `references/card-advice-candidates.md` の表を読んで作る。
  - 規則の文と、1首のページの決まった文（序歌、出典の行、助言の出典の書き方）は `content/karuta/rules.ts` に置く。知識の文章なので `content/` に置き、MIT License の範囲の外にする。規則が当たる札は、`test/site/karuta.test.ts` がスキルの `card-rules.md` の札と件数に照らす。
  - 助言の候補は、スキルの表を組み立てのたびに読む。候補を削るときはスキルの表の行を消す。何首かにまたがる助言の札の名指し（「大山札の6首」など）は `site/karuta.ts` が規則に当て、知らない名指しは組み立てを止める。
  - 100首の一覧は、決まり字の発音の最初の音で分け、読み方一覧の音の順を保って札の数で並べる。3つの並び（決まり字順の2つの向き、歌番号順）を HTML に入れ、JS で見せる並びを選ぶ。JS がないときは決まり字順（多い→少ない）だけを出す。
  - 本文で札を指すときは `{{札 番号}}` と書き、組み立てが決まり字のリンクに置き換える。画面に歌番号を出さない決まり（`docs/ui-guide.md` の7節）を、書く人が番号で札を指しながら守るためである。
  - 日本語の名前の Markdown は、先頭の `slug` で英字の URL に置く。読んだ行には日本語のファイル名を出す。
  - 余韻で伸ばす最後の音（結句の発音の最後の字）を1首のページに出し、「ポイントを知る」には最後の音ごとの弱め方の練習を作者の経験として足した（2026-11-05 の依頼。根拠はスキルの `timing.md` の「作者の見解」）。最後の音ごとの札の数は書き写さず、組み立てのたびに表から数える。#24 で20番と77番の最後の音が変わるからである。
- 理由：表が変わったとき（発音を一覧の表記にそろえる #24 など）にページが追いつく。規則が当たる札を全札分そろえて出せる。候補をスキルに1か所だけ置けば、教科書とスキルの答えが食い違わない。
- 入れないと決めたもの：
  - 「を」の読み分け。教科書の歌では、「を」の字にも、「を」を含む漢字の語の読みの「を」の所にも「お」を振らない（「小倉山」は「をぐらやま」と振る）。読み方一覧は「を」の一部にだけ「お」のふりがなを付けていて、どれに付けるかが読み分けそのものだからである。読む画面のふりがな（を→お、`docs/ui-guide.md` の7節）と、一覧で26番を「お」に入れる決まり（同じ節）は前からあり、このページと食い違う。どちらに合わせるかはユーザーが決める。「を」に掛かる注（62番）、「を」で始まる26番を母音で始まる札や出だしが同じ札に数えることも出さない。
  - 44番と93番の二句の伸ばし方と、改訂の前の二句の読み。
  - 母音の無声化の「作者の見解」。候補の一覧になく、作者個人の考えだからである。
- 採らなかった案：
  - 101ページを Markdown で書く案。表を直すたびに101ページを直すことになる。
  - 助言の候補を `content/` に写して選ぶ案。今は候補を全部出す段階で、写すと候補が2か所になる。ユーザーが選ぶ段になったら、選んだ行の一覧を `content/` に置く形を改めて考える。
  - 規則の文をスキルの `card-rules.md` の「決まり」の行から読む案。行はスキルの答え向けの書き方で、資料の件数の注記などを含み、1首のページの文にならない。
- 限界：
  - 句切れと掛詞は表に列がないので、`card-rules.md` が冊子を目で数えた札をそのまま使い、歌のどこかは示さない。
  - 総論（B1）の帯は、お手本の音声の配信（E1）がないので、動かさない図だけにした。「実際の読みで確認する」とお手本の再生、「この札で読む」はまだない。

## 2026-11-04 読む画面を、区切りと朱の進みだけの形にする

- 決めたこと：
  - お手本を聞く画面と読む画面の歌の枠を、同じ形にする。歌を「下の句5秒」「余韻3秒・間1秒」「上の句6秒」の3つの区切りに分け、右から並べる。見出しも本文も縦書きにする。
  - 時間とともに変わるのは、次の2つだけにする。
    - 字の朱の塗り：字ごとに、その字の始まりから次の字の始まりまでに上から塗る。
    - 今の区切りの囲み：黒の 2px の線で、0秒、5秒、9秒に移る。
  - 歌の枠には、上の帯、地の減り、区間名と残り秒数、秒数の札を出さない。帯は導入の段1と総論で使い、数字に「秒」を付ける。
  - 字の時刻（C3）は、札の読みの表から、拍と伸ばしの重みで、5-3-1-6 の標準の時間に割り振る。重みは、拍が 1、伸ばす印が 2 である。
  - 余韻の印は、上から下へ細くなる三角にする。余韻に入ったら早めに弱め始める「にんじん型」（講習資料 s.25）に合わせる。
  - 字の時刻はいつも拍で作る。下の句が漢字で終わる札では、最後の漢字を自分の拍の範囲で塗る。
  - 余韻と間の区切りの本文は、下の句の最後の字と余韻の印だけにする。間の1秒は何も塗らない。
  - 歌の中の朱は、読み上げた字だけに使う。伸ばす印、余韻の印、決まり字は字と同じ色にする（1首のページも）。
  - 歌の表記は、最初をかな（発音どおり）にする。切り替えは歌の左上に置く。
  - 余韻の入りでタップして数え直す作りは、なくす。読む前の説明は、合図の1項目にする。
  - 導入の段は3つにする（帯と色を説明する段をなくす）。
- 経緯：
  - 見本を触ってもらった初心者から、読む間は朱の字を追うので精一杯で、帯と秒数は目に入らず、地の減りはノイズになる、というフィードバックを受けた。
  - ユーザーが UI を決めきってから実装に入ると決めた。見本で案を比べて、2026-11-04 の夜に決めた。
  - 細部は `docs/ui-guide.md` の 7〜9節にある。
- 理由：
  - 字が朱になっていくのはカラオケと同じ理屈で、たいていの人は説明がなくても字に合わせて読める。
  - 時間で変わる物を減らすと、字を追うことと読むことだけに集中できる。
- 採らなかった案：
  - 余韻と間の秒数を、歌のそばに出す案（余韻の印の下、上の句の頭、2つの句のあいだのゲージ）。
  - 間を独立の区切りにする案：1秒だけの囲みが跳ねて、せわしない。
  - 字ごとに一気に朱にする案：伸ばす長さが分からない。
  - 余韻の印のあとに「（間）」と書いて間の1秒で塗る案：ユーザーが何回か試し、かえって読みづらかった。
  - 余韻の印を、上が四角、下が三角の五角形にする案：全部三角だと始めから弱めると誤解される、として試したが、音量を保つ「だいこん型」に近く読め、資料と食い違う。
  - 下の句の最後の漢字を丸ごと 5.0 秒から塗る案：かなと漢字の表記で、下の句の時刻がずれる。
  - 札の仮名で出す全ひらがなの案。
  - 字数で等分する時刻：要件 C3 が誤った手本として禁じている。
- 限界：
  - 字の時刻は標準の時間の中の割り振りで、お手本の音とは合わない。
  - 幅 320 では、歌の字が 10.9px まで縮む。
  - 実機では確かめていない（iPhone SE のシミュレーターと Chromium で確かめた）。

## 2026-11-03 平日の昼に自走を順に進める

- 決めたこと：
  - `auto.yml` を cron で、日本時間の平日 9:00〜18:30 に30分ごとに起こす。cron は UTC で `*/30 0-9 * * 1-5` と書く。日本の祝日は見分けない。
  - `work` が成功したら、`next` の job が `auto.yml` を `workflow_dispatch` で起こす。番号は渡さない。平日の 9:00〜18:30 の外と、失敗のあとは起こさない。
  - どの実行も、起動のきっかけによらず、`auto-target.sh` がいまの状態から対象を選ぶ。順は、渡された PR、修正を待つ PR、Issue である。修正を待つ PR は、Claude の開いた PR で、最新の `review-gate` が赤で、`needs-human` がなく、レビューの回数が `review-gate.sh` の `MAX_ROUNDS` を超えていないものとする。
  - 日本時間の1日に始める Issue を5件までにする。`work` が付ける `in-progress` の、今日の回数を数える。`in-progress` を付けたあとに失敗した実行は数え、準備の段階（checkout、依存の導入）で落ちた実行と PR の修正は数えない。
  - 本文の `Depends:` を含む行の `#番号` を、行の数によらずすべて依存として読む。1つでも開いていれば飛ばす。
  - Claude の action に、`additional_permissions` で contents、pull_requests、issues の3つを書いて求める。すべての Workflow の Claude の step が、GITHUB_TOKEN か、この3つだけを求めたトークンを使うことを `checks.test.sh` で確かめる。
- 理由：
  - ユーザーが手を動かさなくても、平日の昼に Issue から PR まで続けて進むようにする。
  - `concurrency` の保留は1本で、新しい起動が来ると前の保留は取り消される。ラベルをまとめて付けると途中の起動が消える。Issue の実行の途中に `review-gate` が起こした修正の実行も、その実行の終わりに起こす次の実行や cron に押し出される。起動に意味を持たせず毎回状態から選べば、押し出されても次の実行が同じものを拾う。
  - 公開の `GET /apps/claude` を読むと、Claude の App は `workflows: write` を求めていた。action の FAQ の「Workflow の書き込みの権限がない」と食い違う。action は `additional_permissions` を書いたときだけ、求める権限を交換のサーバーへ送る。書かないときの範囲はサーバーが決める。
- 判断：
  - cron は朝の始まりと、失敗や押し出しのあとの拾い直しの役である。間隔は、止まった流れが動き出すまでの待ちの上限になるので、30分にした。実行の途中に来た cron は保留になり、次の実行として動く。
  - 失敗のあとは次を起こさない。鍵の期限切れのような原因では、残りの Issue を次々に `needs-human` にしてしまう。30分ごとの cron と1日の上限で抑える。
  - 平日の昼の外では次を起こさない。夜にラベルを付けた実行は動くが、続きは翌朝の cron に任せる。夜にユーザーと手元で作業する分と、Claude の利用枠を取り合わないためである。

## 2026-11-02 音声と鍵の書き込みを hook で止める

- 決めたこと：`.claude/settings.json` の PreToolUse の hook で、Write、Edit、NotebookEdit、Bash を検査する。リポジトリの中へ音声や鍵のファイルを書く操作と、鍵らしい文字列を含む操作を止める。
- 理由：`.gitignore` は `git add -f` を止めない。CI が動くのは PR を開いたあとである。hook なら書く前に理由を Claude に返せるので、置き場を変えて続けられる。
- 試行錯誤：最初の実装はリポジトリの中のパスだけを見ていて、`cp /外/a.wav tests/` を通した。音声の名前がコピー元にしか出ないからである。先に書いたテストで見つかり、コピー系のコマンドは最後の引数をコピー先として扱う形に直した。
- 試行錯誤：直したあとも、`cp /外/a.wav tests/ 2>/dev/null` を通した。最後の引数が `/dev/null` になるからである。セルフレビューで見つかり、リダイレクトを除いてからコピー先を決める形に直した。
- 採らなかった案：Bash の引数をすべて検査する案。`git commit -m "*.wav を除外する"` や `ls a.wav` のような、書かない操作まで止まる。
- 残る穴：スクリプトの中で書かれるファイルと、フォルダーごとのコピーは見えない。この2つは `.gitignore` と CI の検査で止める。
