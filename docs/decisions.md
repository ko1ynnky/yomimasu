# 判断の記録

あとの作業に影響する技術と設計の判断を、新しいものを上にして書く。理由と、採らなかった案も残す。結論を改めるときは、元の項目を消さずに、改めた日付と理由を足す。

## 2026-11-07 PR にラベルを付けたときと、本文とタイトルを直したときは ci.yml を動かさない

- 決めたこと（ユーザーが認めた）：
  - `ci.yml` の `pull_request` の types を `[opened, synchronize, reopened]` にする。`labeled` と `edited` を外す。
  - `risk-gate` の job を、中身を変えずに `.github/workflows/risk-gate.yml` へ移す。types は `[opened, synchronize, reopened, labeled]` で、concurrency は PR の番号ごとにする。必須の検査は job の名前で結ぶので、設定を変えずに必須のまま残る。
- 理由：
  - PR の実行は同じ PR の前の実行を取り消すので、ラベルを付けたとき（`go:merge` など）と本文やタイトルを直したときに、動いている E2E が初めからやり直しになっていた。2026-11-05 から、12のコミットで CI が2回動き、5回は動き始めて 95〜400 秒で取り消された。
  - `labeled` は、`go:merge` を付けたときに `risk-gate` を動かすためだけにあった。`edited` は、PR の base を変えたときに検査を動かすために足した（25fe57f の「fix: 検査の抜け道を閉じる」）。本文とタイトルを直したときも `edited` が起きる。
- 引き換え：`edited` を外したので、base を `main` に変えた PR では、`ci.yml` も `risk-gate.yml` も動かない。必須の検査は待ちのまま残り、マージできない（止まる側に倒れる）。push するか、PR を閉じて開き直すと動く。`production` のブランチは作っていないので、`production` を base にした古い検査で通ることもない。
- 採らなかった案：`ci.yml` の job を、`github.event.action` を見る `if` で飛ばす案。飛ばした job は「skipped」の検査を同じコミットに出し、前の失敗を上書きして通った扱いになる。抜け道になる。

## 2026-11-07 CI の E2E をファイルの組に分けて5台で並べて流し、apt を使わない

- 決めたこと：
  - `ci.yml` の E2E を、matrix の `e2e-shard` の5つの組に分ける。組ごとに別の runner で、`--workers=1` で流す。必須の検査の名前 `e2e` は、組の結果をまとめる job の名前にする。どの組も通ったときだけ通し、組が落ちても時間切れでも、飛ばされずに赤で終わる。
  - ファイルを組に分ける表は `ci.yml` の `SHARD_FILES` に置く。1行に「組の番号 ファイル」を書く。前の組は `--test-list` で表のファイルだけを流し、最後の組は `--test-list-invert` で、表で前の組に入れなかったファイルをすべて流す。新しいファイルは最後の組に入る。組の番号は `strategy.job-index` から数えるので、matrix の数を変えても、どの組にも入らないファイルは出ない。
  - いまの組：1 は kv-lens、2 は result と listen-back、3 は record と next-point、4 は records、kv、flow、5 は残りの11ファイル。
  - Playwright のブラウザーは、`~/.cache/ms-playwright` を `actions/cache` で `@playwright/test` の版ごとに残し、`npx playwright install chromium` で入れる。`--with-deps` は付けない。
  - `--with-deps` が入れていた日本語と中国語のフォント（`fonts-ipafont-gothic`、`fonts-wqy-zenhei`）は、.deb を同じキャッシュに残し、`dpkg -i` で入れる。apt から取るのは、キャッシュにないときだけである。入れたあとに `fc-list :lang=ja` が空なら落とす。
    - 試行錯誤：はじめは .deb を `apt-get install` に渡していたが、PR #76 の最初の実行で、同じ版を apt のリポジトリから取り直していた（`Need to get 11.0 MB of archives.`）。キャッシュがあっても apt の取得が残るので、`dpkg -i` に替えた。入るのはこの2つだけで、ほかに足りないパッケージはなかった（`2 newly installed`）。
    - 同じ実行で、入れる前の runner に日本語のフォントがないことも確かめた。apt は2つを新しく入れ（`The following NEW packages will be installed`）、入れたあとの `fc-list :lang=ja` は IPAGothic と WenQuanYi Zen Hei Mono の2つだけだった。
  - 組の上限は10分にする。`after-merge.sh` が15分待つ理由の注記を、この上限と、そのあとに動く `e2e` に合わせて直した。
- 理由：
  - PR のマージが `e2e` を待っていた。ほかの検査は1分かからないが、`e2e` は14〜23分かかった（`ci.yml` の直近約100回）。`npm run e2e` の step が13〜16分で、213件を1 worker で流し、1件ごとの時間の合計は 767 秒だった（run 42236921683）。録音を実時間で流すテストが多く、時間は CPU ではなく待ちである。runner を分ければ、待ちが並んで進む。
  - 1台の中の workers は1のままにする。公開すると runner は4 vCPU になり、Playwright の既定（論理コアの50%）では2になる。提出の直前に、録音の E2E の時間の条件を変えない。
  - `--with-deps` の apt は、ふだん20〜40秒だが、直近8回のうち2回は取得が 37 kB/s に落ちて9〜10分かかった。ubuntu-latest には Google Chrome とその依存のライブラリーが入っている。
  - ubuntu-latest の apt のパッケージの一覧（runner-images の Ubuntu2404-Readme、20261101 の版）に載っているフォントは `fonts-noto-color-emoji` だけで、日本語のフォントはない。アプリは Web フォントを持たないので、フォントがないと字が豆腐で描かれる。豆腐は全角の字より幅が狭く、横スクロールの検査がはみ出しを見逃し、画面の画像も読めなくなる（PR 前のレビューの指摘）。今までと同じ2つのパッケージを入れ、字の幅の条件を変えない。
- 分け方を決めた手順：
  - Playwright 1.64.1 の `--shard` は、時間を見ずに、テストの件数で前から順に切る（`node_modules/playwright/lib/runner/index.js` の `filterForShard`）。`--fully-parallel` を付けると1件ずつ切れる。
  - `--list --fully-parallel --shard=i/N` の一覧に run 42236921683 の1件ごとの時間を当てると、4組で 159、162、382、64 秒になった。遅いファイル（record、records、result）が名前の順で隣り合うので、1つの組に集まる。3〜10組のどれでも、最も遅い組は 207〜459 秒で、組を増やしても単調には減らない（8組で 207 秒、9組で 313 秒）。
  - ファイルごとの時間（秒）は、result 150、record 133、kv-lens 92、records 84、next-point 62、shell 62、listen-back 44、kv 31、flow 28、install 24、listen 18、残りの8ファイルで合わせて 40 である。
  - 試行錯誤：はじめはこの1回の時間で4組（result と listen-back、record と next-point、kv-lens と kv と records、残り）に分け、193、196、207、171 秒と見積もった。PR #76 の最初の実行では、3つ目の組の E2E の step が 356 秒かかった。kv-lens が 198 秒、kv が 65 秒で、見積もりの2倍だった。ほかの組は見積もりとの差が7秒以内だった。
  - 1台で流していたころの6回（run 42240460788 から 42244731719）を見ると、kv-lens は 87〜197 秒、kv は 29〜64 秒、shell は 62〜87 秒で、速い回と遅い回の2つに分かれる。録音のテスト（result、record、records）は、どの回も差が数秒である。画面の絵を描く CPU の重いテストだけが、runner の速さで変わると見られる。
  - そこで、6回のそれぞれに組の表を当て、最も遅い組の時間で比べた。4組の初めの表は最大 345 秒、4組で組み直した表（kv-lens と listen-back、result と records、record と next-point と flow、残り）は最大 251 秒、いまの5組の表は最大 203 秒だった。5組の表は、速い回で 87、193、195、143、134 秒、遅い回で 197、196、202、178、177 秒になる。新しいファイルが入る最後の組は軽くしてある。
- 結果（PR #76 の実行。時間は GitHub の job と step の記録から）：
  - 前：`e2e` の job は14〜23分。`npm run e2e` は13〜16分、`playwright install --with-deps` は20〜40秒（遅い回は9〜10分）。
  - 5組、キャッシュあり（run 42250216262）：組の job は 207〜237 秒、`E2E` の step は 174〜204 秒。ブラウザーとフォントを入れる step は合わせて 3〜6 秒で、キャッシュを戻すのに 6〜9 秒かかった。apt からは何も取っていない。実行を始めてから `e2e` が通るまで4分7秒。テストの数は 18、10、25、20、140 で、合わせて 213。
  - 4組、キャッシュなし（run 42248234879、上の試行錯誤の表）：ブラウザーの取得は 8〜13 秒、apt からのフォントの取得は 13〜35 秒。3つ目の組が遅い runner に当たり、`e2e` が通るまで7分8秒だった。
  - どちらの実行でも、`--with-deps` なしで Chromium が起動し、213件がすべて通った。落ちたテストと、やり直して通ったテストはない。画面の画像の日本語は豆腐になっていない。
- 採らなかった案：
  - `--shard` と `--fully-parallel` だけで分ける案。上のとおり、4組で最も遅い組が 382 秒になり、目標の約4分を超える。ファイルで分けるいまの形では `--fully-parallel` は効かないので付けない。1つの組の中は、今までどおりファイルの中の順に流れる。
  - `PWTEST_SHARD_WEIGHTS` で組の件数の比を変える案。文書にない内部の環境変数で、件数で切る形は変わらず、テストを足すと境目が動く。
  - 4組の案。上のとおり、遅い runner に当たると最も遅い組が約250秒になり、目標の約4分を超える。5組では、速い runner に当たった kv-lens の組が1分半で終わって台が余るが、どの組が遅い runner に当たるかは選べないので、遅い回に合わせた。
  - 1件ごとの時間の表をリポジトリに置き、実行のたびに組を計算する案。表と計算のスクリプトの手入れが要る。
  - `fullyParallel` を設定に書く案。手元の `npm run e2e` の流し方が変わる。
  - フォントを毎回 apt で入れる案。取得が遅い回を避けられない。Web フォントを足す案は、アプリの画面を変える。
- 限界：
  - 組は手で直す。ファイルの時間が変わったら、表の行を動かす。新しいファイルは最後の組に入るので、増えるとそこが遅くなる。
  - 1つのファイルが1つの組の目安より長くなったら、表の1行をファイルの中のテストに分ける必要がある。`--test-list` は「ファイル › テストの名前」も受けるが、いまの awk は2列目だけを読む。
  - matrix の値（job の名前の番号）と、実際に流す組（job-index）は、matrix を並べ替えると食い違う。
  - キャッシュは PR のブランチと main で分かれる。PR の最初の実行は、main にキャッシュがなければブラウザーを取りに行く。

## 2026-11-06 公開の前に、deny-names で main の外のコミットと、Issue と PR の文も見る

- 決めたこと：
  - `deny-names.sh` に `SCAN_REFS=1` の形を足す。ブランチ（`refs/heads/` と `refs/remotes/`）、タグ、PR の参照（`refs/remotes/pull/<番号>`）から辿れて HEAD から辿れない各コミットで、コミットメッセージ、足した行、足したか名前を変えた先のファイル名を見る。足した行とファイル名は、`SCAN_HISTORY` と同じ関数で見る。
  - いくつもの参照から辿れるコミットは、PR の番号の小さい順、次にブランチとタグの名前の順で、最初の参照の分として1回だけ見る。ログには `PR #<番号>` かブランチの名前と、SHA と件数だけを出す。ブランチとタグの名前も公開されるので、名前に一致した参照は「名前を伏せた参照」と出し、その数も一致として数える。

## 2026-11-06 公開の前に、deny-names で履歴の足した行とファイル名を見る

- 決めたこと：
  - `deny-names.sh` に `SCAN_HISTORY=1` の形を足す。`SCAN_BASE` から HEAD までの各コミットについて、1つ目の親との差分で足した行と、足したか名前を変えた先のファイル名を見る。足した行は `+` で始まる行で、ファイルの頭の `+++` を除く。`SCAN_BASE` が根のコミットかすべて0なら、根も含めて HEAD までの全部を見る。
  - 一致したら、コミットの SHA と件数だけを出す。行も、パスも、名前も出さない。
  - `ci.yml` の `workflow_dispatch` に真偽の入力 `scan_history`（既定は false）を足し、手動の起動のときだけ `SCAN_HISTORY=1` にする。PR と push の検査は変えない。手動の起動は今までどおり `main` の版のスクリプトを使うので、この形はマージしてから使える。
- 理由：リポジトリを 2026-11-07 ごろに公開する。今までの `deny-names` は今の版のファイルとコミットメッセージだけを見るので、古いコミットで足してあとで消した名前を見つけない。公開すると、その名前も履歴から読める。ユーザーが 2026-11-06 に、公開の前の履歴の検査を認めた。Actions のログも公開されるので、今までの名前の検査と同じく、場所と件数だけを出す。
- 採らなかった案：
  - PR と push でも履歴を見る案。公開の直前に必須の検査の動きを変えることになる。
  - 一覧を手元に置いて、手元で履歴を調べる案。一覧は secret にだけ置く。
- 限界：
  - `main` から辿れるコミットだけを見る。スカッシュでマージした PR の途中のコミットと、ほかのブランチは見ない。公開すると、これらのコミットも PR の画面から読める。
    - 2026-11-06 に改めた点：手動の起動の `scan_refs` で、これらのコミットも見るようにした（上の項目）。
  - 範囲より前に足して範囲の中で消した名前は見つけない。根から見れば起きない。
  - `SCAN_HISTORY` を読まない版のスクリプトは、履歴を見ずに通る。起動したら、ログに「N 件のコミットで、足した行とファイル名を見ました。」が出たことを確かめる。
  - 一致が出たときの直し方は決めていない。`main` を書き換えても、スカッシュした PR の参照（`refs/pull/N/head`）に同じ中身が残り、利用者からは消せない。一致を出した実行のログ（SHA と件数）も、公開すると読める。

## 2026-11-06 入口の題の下に、決まり字で組んだ読手の動く絵と「↓」を置く

## 2026-11-06 録音と結果を端末の IndexedDB に残し、前回と比べる画面を作る

- 決めたこと（Issue #43、C8）：
  - 読み終えたらすぐ、録音（`Take`）と測定の結果を、そのブラウザーの IndexedDB に残す。ログインはなく、端末の外へ送らない（2026-11-02 のユーザーの判断）。
  - 記録と音は別の置き場に分ける。記録には組、補助の有無、録った時刻、測定の結果を入れ、音には PCM、標本化周波数、読み始めの位置、声の処理の設定を入れる。
  - 結果は残すときに1回だけ測り、記録に入れる。一覧を開くたびに測り直さない。
  - `Take` に声の処理の設定（`voiceProcessing`）を入れる。残した録音でも、音量の参考値を出すかを録音ごとにあとで決められるようにするためである。`measure` に `autoGainControl` を渡さないのは今までどおりで、音量の参考値は出さない（`docs/measure.md`）。

    - 新しい2件を前回と今回として、結果の画面と同じ行、目安、判定の語で並べる。組が違っても並べ、列の見出しに組の決まり字と補助の有無を出す。
    - 前回と今回の録音を、読み始めの位置から鳴らせる。
    - 間の平均とばらつきは、間を測れた回が2回以上あれば、残っている全部の録音から出す。平均は 0.01 秒の値から求め、0.1 秒に1回だけ四捨五入する。ばらつきは、いちばん短い回と長い回の差である。どちらも判定の語を付けない。
    - 録音は1件ずつと全部を消せる。全部を消すときだけ、消す前に確かめる。
  - 結果の画面は、開いている画面の録音がなければ、端末に残した最後の録音を出す。ただし、最後に読んだ録音を残せなかったときは、前の録音を出さない。残せなかったことは sessionStorage に覚える。
  - 録音が1件でも残っていれば、結果の画面の「次は？」に「前回と比べる」を置く。
  - 録音の画面の注記を「録音は端末に残り、外へ送りません。」にする（ガイド9節）。「あとから消せます」は書かない。
  - 2026-11-06 の朝に、ユーザーが次の3つを認めた。注記に「あとから消せます」を書かないこと。「前回と比べる」を、録音が1件のときから出すこと。1件ずつ消すときは確かめず、全部を消すときだけ確かめること。
- 理由：
  - 1本を測るのに、23秒の合成音で約 90 ms かかった（Node、M5 の Mac、3回）。端末ではこの数倍かかるので、一覧を開くたびに全部を測り直すと待たせる。
  - 音を記録と同じ置き場に入れると、一覧を開くたびに、1本で約 5 MB（27秒、48 kHz、32 ビット）の音を全部読み込む。
  - ばらつきを最短と最長の差にしたのは、2〜3回でも値が揺れにくく、選手と保護者に「1.0〜1.6秒」の形で伝わるからである。差は見せる 0.1 秒の値どうしで取り、並べた秒と食い違わないようにした。
  - ばらつきに判定の語を付けないのは、ばらつきの幅の目安が測定の定義にないからである。新しい目安を決めるのは測定の定義の変更になる。
  - 「前回と比べる」を前回の録音がないうちから出すのは、録音を消す操作がその画面にしかないからである。出さないと、録音が1件のうちは消せない（reviewer の指摘）。
  - 注記に「あとから消せます」を足すと、360×560 で録音の画面が 41px はみ出した。注記と「読み方の説明」が1行に収まるのは 18 字までである。
  - 残せなかったことを覚えないと、ページを読み込み直して結果の画面へ移ったときに、前に残した録音の結果を今回の結果として出す（reviewer の指摘）。
- 採らなかった案：
  - 一覧を開くたびに、残した音から測り直す案。定義が変わったあとも同じ定義で並べられるが、上の理由で待たせる。定義が変わったら、残した音から測り直せる。
  - ばらつきを標準偏差で出す案。2〜3回では揺れやすく、伝わりにくい。
  - 平均とばらつきを、補助の有無や組で分ける案。回数が少ないうちは分けると出なくなる。
  - `navigator.storage.persist()` で消されにくくする案。Firefox は許可を尋ねる画面を出すので、読む流れを止める。
  - 残す件数に上限を設け、古い録音を自動で消す案。利用者が消していない録音を消すことになる。
  - PCM を 16 ビットや低い標本化周波数にして小さくする案。測り直したときに値が変わる。
  - 1件ずつ消すときも確かめる案。消す操作が多いと手間になる。消すのは1件だけなので、全部を消すときだけ確かめる。
  - 前回の録音があるときだけ「前回と比べる」を出す案。はじめはこの形にしたが、上の理由で改めた。
- 限界：
  - 残せる量はブラウザーと端末の空きで違う。残せなかったときは知らせず、記録の画面に出ないだけである。
  - Safari は、しばらく開かれないサイトがスクリプトで残したデータを消すことがある。iPhone の実機ではまだ確かめていない。
  - 前回と比べる画面の再生は、この時点ではお手本の再生（PR #22 の `playback.ts`）と1つにしていなかった（PR #52 で1つにした）。
  - 前回と比べる画面にも、ほかの画面と同じく「戻る」とターミナルへの打ち込みはまだない。
  - 記録には、どの定義で測ったかを入れていない。定義が変わると、前の定義の値と今の定義の値を同じ表と平均に並べる。定義を変えるときに、記録に定義の印を足し、印のない記録を残した音から測り直す。

## 2026-11-06 お手本の音声を、公開しないバケットから Worker が同じオリジンで配る

- 決めたこと：
  - お手本の202本は R2 のバケット `yomimasu-audio` に `v1/NNN_N.m4a` の名前で置き、バケットは公開しない。アプリの Worker（`site/worker.ts`）が、同じオリジンの `/audio/v1/NNN_N.m4a` で配る。
  - Worker を静的なファイルより先に通すのは `/audio/*` だけにする（`assets.run_worker_first`）。静的なファイルに当たらないパスは Worker にも来るので、`/audio/` の外は `ASSETS` の束縛に渡し、今までどおりの答えにする。
  - 答えるのは GET と HEAD の `/audio/v1/<3桁>_<1か2>.m4a` だけにする。形の違うパスは、バケットにキーがあっても 404 にする。形の合うパスへのほかのメソッドは 405 にし、`Allow: GET, HEAD` を付ける。
  - Range は1つの範囲に 206 で答え、満たせない範囲には 416 と `Content-Range: bytes */全体の大きさ` を返し、長いキャッシュは付けない。複数の範囲と読めない Range は、RFC 9110 が認めるとおり無視して全体を返す。
  - `Content-Type: audio/mp4`、`Cache-Control: public, max-age=31536000, immutable`、`Accept-Ranges: bytes` は、バケットのメタデータを写さずに Worker で付ける。ETag は R2 の `httpEtag` を使う。
  - `v1/` のキーの中身は置き換えない。音声を直すときは `v2/` のキーに置き、聞く画面の取得先を変える。
  - プレビューにも同じバケットを束ねる。
- 経緯：2026-11-06 にユーザーが、お手本の音声を上げて配ることを決めた（#42）。
- 根拠：
  - 聞く画面は、取得先を同じオリジンのパスに限る（PR #22 の `site/client/playback.ts`）。外の配信から読むと、どの端末が聞いたかが外へ出るからである。
  - Range は iOS の Safari が使う（#42）。
  - パスの形で m4a に限っているので、型は Worker で決められる。上げ方の違いで型やキャッシュが変わらないようにした。
  - キーの中身を置き換えないので、1年の `immutable` で端末にキャッシュさせても古い音が残らない。同じ理由で、`If-None-Match` と `If-Range` は見ない。
  - R2 の Workers API の文書は、満たせない範囲を `get` に渡したときの答えを決めていない。そこで範囲の要求では先に `head` で大きさを見て、範囲を Worker で決めてから `get` で読む。
  - プレビューは、上の階層の束縛を受け継がない。束縛は `previews` に書く。Worker はバケットを読むだけなので、プレビュー用のバケットには分けない。
- 採らなかった案：
  - バケットを公開し、r2.dev の URL で配る案。別のオリジンになり、聞く画面の取得先の制限から外れる。r2.dev は速さが制限され、本番には向かない。
  - バケットを公開し、カスタムドメインで配る案。これも別のオリジンになり、CORS の設定が要る。バケットの中のどのキーも、パスの検査なしに取れるようになる。
  - 音声を `dist` に入れて静的なファイルとして配る案。音声は Git に入れない（2026-11-02）ので、組み立てのたびにどこかから取ってくることになる。
  - R2 の型のために `@cloudflare/workers-types` を足す案。使うのは `head` と `get` だけなので、使う形だけを `site/worker.ts` に書き、依存を増やさない。
- 限界：
  - Worker の答えは Cloudflare の CDN のキャッシュに載らないので、毎回 R2 から読む。端末のキャッシュは1年である。要るようになったら Cache API を試す。
  - 範囲の要求は R2 の操作を2回使う（`head` と `get`）。

## 2026-11-05 測定の定義を決め、選択と値を1か所のデータに置く

- 決めたこと：
  - ユーザーが D1 の定義を決めた（2026-11-05）。声の区間は `voiced-level-20` で、声と背景の差が 20 dB 未満なら測らない。余韻は最後の音の子音の始まりから数えるが、秒数は出さない。決まり字までの速さは、お手本の区切りの値を読手に確かめるまで出さない。声の大きさは、自動の音量調整が切れていると確かめた録音だけで出す。誤差の目標に届かない項目は出さない。

  - 物音は、0.25 秒未満の切れ目をつないだまとまりのうち、声だった長さの合計が `noise.minPhraseSec` 未満のものとし、間を選ぶ前に除く。
  - `Measurement` は項目ごとに、値か測れない理由を持つ。測る範囲の端で声が切れていれば、その端を使う項目だけを測れないとする。

- 理由：値を変えるとき、データの行と表の行を直せば、Web とスキルとテストが同じ定義になるようにする。合図の間の音と、読み終えてからボタンを押すまでの音で、間が変わらないようにする。
- 余韻の秒数を出さない理由：録音だけから最後の音の始まりを取る方法を比べたとき、0.1 秒以内に入るのは最もよい方法で半分ほどだった。お手本の区切りを写す方法でも 72〜83% で、90%点の目標 0.1 秒に届かない。
- 採らなかった案：
  - まとまりの端から端までの長さで物音を判断する案。部屋の音に混じる一瞬の周期の音が、読み終えたあとの短い声とつながって物音の長さの上限を超え、上の句か間が変わった。
  - つなぐ前に 0.05 秒未満の区間を捨てる案。前後の音では値が動かなくなったが、句の端の短い区間も消え、間の誤差の絶対値の中央値が 0.005 秒増えて目標を外れた。
  - 読み始めの位置ちょうどから測る案。帯が動くのと同時か少し前に出た声の頭が切れる。
  - データを JSON に置く案。値ごとに採らなかった案を書けず、選べる値を型で縛れない。
  - 声の区間の候補 `floor-45-30` と `speech-20-15`。閾値を測る範囲全体の音量の分布から決めるので、前後に物音を足すと値が動いた（最大 0.02 秒と 0.13 秒）。`speech-20-15` は声の消え際を切るので、間が 0.17 秒長く出た。
- 限界：
  - 人が付けた正解データとはまだ比べていない。
  - 読み終えたあとに `noise.minPhraseSec` 以上話すと、上の句か間を取り違えるおそれがある。合成音と録音では、0.35 秒までの声を確かめた。

  - `main` と `production` への push の実行は取り消さない。取り消すと、そのコミットのメッセージを誰も見なくなる。
  - Action は版のタグではなくコミットの SHA で固定する。
- 理由：
  - 一覧が2か所にあると、片方だけ直したときに穴になる。
  - 検査できないときに通すと、検査がないのと同じになる。hook と同じ考え方である。
  - `deny-names` は secret を読み、`risk-gate` は PR を書き換える。自動の実行が作る PR でスクリプトを変えて通せないようにする。
- 判断：検査のログは公開されるので、鍵と名前の検査は場所だけを出し、一致した行を出さない。`deny-names` はファイル名に一致したときもパスを出さず、件数だけを出す。パスを出すと、一覧の中身が分かるからである。`no-audio`、`no-secrets`、`risk-gate` はパスを出す。ファイル名は PR の差分で公開済みで、直す人に要る。
- 判断：`risk-gate` の許可には、測定、録音、知識の文章、依存、設定を入れない。`go:merge` は自動でマージするので、許可は狭く始める。
- 試行錯誤：検査のテストを書いた直後の確認で、スクリプトがなくても「落ちる」期待のテストが exit 127 で通っていた。落ちる期待は exit 1 だけを認める形に直した。
- 採らなかった案：gitleaks などの Action を使う案。依存を増やさず、hook と同じ形で見られる。
- 試行錯誤：Linux のコンテナーで通して、`git ls-files` が日本語のパスを引用符付きで出し、音声、鍵、名前のファイル名の検査が空振りすると分かった。手元の Mac は `core.quotepath` が false で隠れていた。`-z` で受ける形にして、テストのリポジトリを CI の既定に揃えた。

- 試行錯誤：2回目のレビューで、どの理由の失敗でも取り出した版へ切り替わること、切り替わりがログに残らないこと、`git grep` の失敗のテストが別の行で先に止まり守れていないことが分かった。切り替えの条件を絞り、`git grep` だけを失敗させる偽の `git` でテストした。
- 採らなかった案：`pull_request_target` で base の Workflow を動かす案。secret を持つ Workflow が PR の内容を扱う形は、外部の入力を閉じる考え方と合わない。`deny-names` は PR の本文を読むので、PR のコードを実行しない形なら作れるが、下の限界の前提が崩れるまでは使わない。
- 限界：
